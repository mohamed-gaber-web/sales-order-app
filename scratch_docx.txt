1. Direct Connection Model (No Middleware)
The mobile app connects directly to Dynamics 365 Finance & Operations over the internet. There is no middleware layer: the app authenticates to Entra ID, receives a token for F&O, and calls F&O REST endpoints (OData data entities and custom X++ services) directly. The app is assumed to be always online at the point of transaction.
1.1 Two Kinds of System API in F&O
OData data entities: the entity's public name is the API name, called under /data. Used for reads (master data) and simple creates (e.g., SalesOrderHeadersV2).
Custom services (X++): a Service Group / Service / Operation is exposed under /api/services. Used for atomic posting that OData cannot do in one call (invoice post + ZATCA, payment + settlement, return vs. original invoice).

2. Authentication — Direct to F&O (Entra ID)
The app is registered in Entra ID as a public/mobile client and requests a token whose resource is the F&O environment. The signed-in rep maps to a D365 user, so every document is stamped with the real user and honors D365 security roles.
2.1 Token request
POST https://login.microsoftonline.com/{tenantId}/oauth2/v2.0/token
grant_type=authorization_code // Auth-code + PKCE for per-user token
client_id={mobileAppRegistrationId}
code={authCode}
code_verifier={pkceVerifier}
redirect_uri=msauth://com.ikk.vansales
scope=https://ikk-prod.operations.dynamics.com/.default
Result: access_token (Bearer) + refresh_token. The token is sent on every F&O call. For service/background jobs a client-credentials token can be used instead.
2.2 Standard headers on every F&O call
Authorization: Bearer {access_token}
Content-Type: application/json
OData-MaxVersion: 4.0 // OData calls
OData-Version: 4.0
If-Match: * // required for PATCH/DELETE
D365 security: the token's user must hold the Van Sales duty/privileges (customer create request, sales order & invoice, payment journal, return order, inventory transfer). No pricing or discount logic is placed on the device — F&O evaluates trade agreements and promotions.

5. Sales Order, Invoice & ZATCA E-Invoicing
5.1 SalesOrderHeadersV2 — انشاء أمر بيع (OData)
POST /data/SalesOrderHeadersV2
Direct OData create for pre-sales/delivery routes. Lines carry resolved price/discount and any promotion reference. Header holds an idempotency key in a custom field.
POST /data/SalesOrderHeadersV2
{
"dataAreaId": "ikk",
"OrderingCustomerAccountNumber": "CU-004512",
"DefaultShippingWarehouseId": "VAN-07",
"DeviceTransactionId": "b1f2-...-9ac"
}
// then POST lines:
POST /data/SalesOrderLinesV2
{
"dataAreaId":"ikk","SalesOrderNumber":"{returned}",
"ItemNumber":"P-1001","SalesUnitSymbol":"CTN",
"OrderedSalesQuantity":6,"SalesPrice":142.00,"LineDiscountPercentage":5.0
}
5.2 GPVanSalesService/postInvoice — ترحيل الفاتورة (Service)
POST /api/services/GPVanSalesGroup/GPVanSalesService/postInvoice
The core call. Since the app is online, this single X++ operation runs the whole cycle inside F&O in one transaction: create order → confirm → post packing slip against VAN-07 → post invoice → compute VAT → invoke the Electronic Invoicing (ZATCA) service → return the fiscal number and QR. Idempotent by DeviceTransactionId.
Request
{
"_request": {
"DataAreaId": "ikk",
"DeviceTransactionId": "b1f2-...-9ac",
"CustomerAccount": "CU-004512",
"Warehouse": "VAN-07",
"DeviceInvoiceNo": "VAN07-000319",
"PaymentMode": "Credit",
"Latitude": 30.0131, "Longitude": 31.2089,
"Lines": [
{"ItemNumber":"P-1001","Unit":"CTN","Qty":6,"Price":142.00,"LineDiscountPct":5.0},
{"ItemNumber":"P-1002","Unit":"CTN","Qty":4,"Price":96.00},
{"ItemNumber":"P-1003","Unit":"PCS","Qty":2,"Price":0,"PromotionId":"PROMO-OIL-6"}
]
}
}
Response
{
"Status": "Posted",
"SalesId": "SO-091233",
"InvoiceId": "INV-091233",
"ZatcaInvoiceHash": "NWZlY2ViNjZmZ...", // SHA-256, base64
"ZatcaQrBase64": "ARvYtNix2YPYqSBJS0s...", // TLV, base64 (goes on the print)
"FiscalInvoiceNo": "SA-2026-556677",
"ClearanceStatus": "Reported", // Reported (simplified) | Cleared (standard)
"Totals": {"Gross":1236.00,"Discount":42.60,"Vat":183.80,"Net":1409.14}
}
System mapping: GPVanSalesService wraps SalesTableType + SalesFormLetter (Confirm → PackingSlip → Invoice) and calls the standard Electronic invoicing feature (RCS-configured, ZATCA format). The app prints directly from ZatcaQrBase64 + FiscalInvoiceNo.
5.3 GPVanSalesService/getEInvoiceQr — استرجاع الـ QR
POST /api/services/GPVanSalesGroup/GPVanSalesService/getEInvoiceQr
Optional re-fetch of the QR/fiscal number for reprint, keyed by DeviceTransactionId or InvoiceId.
{
"InvoiceId":"INV-091233",
"ZatcaQrBase64":"ARvYtNix2YPYqSBJS0s...",
"FiscalInvoiceNo":"SA-2026-556677"
}
5.4 ZATCA QR content (what F&O returns)
The QR is a Base64-encoded TLV (Tag-Length-Value) string built by the Electronic Invoicing feature. Tags, in order:
Tag
Field
Example
1
اسم البائع / Seller name
شركة IKK للأغذية
2
الرقم الضريبي / VAT number
300012345600003
3
التاريخ والوقت / Timestamp (ISO 8601)
2026-08-02T10:07:00Z
4
الإجمالي شامل الضريبة / Invoice total
1409.14
5
قيمة الضريبة / VAT total
183.80
Phase-2 simplified invoices additionally embed the invoice hash, ECDSA signature, and public key (tags 6–8) — all produced by F&O's Electronic Invoicing (the app never signs). The app only renders ZatcaQrBase64 into a QR image and prints it.

8. Errors, Idempotency & Print Flow
8.1 Idempotency (always-online safety)
Every write carries DeviceTransactionId (a client GUID).
F&O stores it (GPIntegrationLog); a repeated call returns the original result rather than re-posting — protects against double-tap and network timeouts even without a middleware queue.
8.2 Standard F&O error shape
{
"error": {
"code": "CREDIT_LIMIT_EXCEEDED",
"message": "تجاوز حد الائتمان — المتاح 16,339"
}
}
8.3 Key error codes
Code
Meaning
App behavior
CREDIT_LIMIT_EXCEEDED
Invoice > available credit
Block; show available amount
CUSTOMER_ON_HOLD
Customer not activated
Cash only; block credit invoice
INVALID_ORIGINAL_INVOICE
Bad return reference
Require a valid invoice
ZATCA_SUBMISSION_FAILED
E-invoice rejected by ZATCA
Retry post; keep invoice unissued
PERIOD_CLOSED
Fiscal period closed
Alert supervisor
TXN_DUPLICATE
DeviceTransactionId seen
Treat as success; reprint
8.4 In-app print flow (ZATCA)
1. App calls GPVanSalesService/postInvoice.
2. F&O posts the invoice and runs Electronic Invoicing (ZATCA), returning FiscalInvoiceNo + ZatcaQrBase64 + hash.
3. The app renders ZatcaQrBase64 into a QR image and lays out the bilingual simplified tax invoice (80mm).
4. The app prints to the Bluetooth thermal printer (or the OS print dialog / PDF).
5. For reprints, the app re-fetches via getEInvoiceQr or prints from its local copy — the QR/fiscal number never change for a posted invoice.
